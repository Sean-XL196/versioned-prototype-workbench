VERSIONED PROTOTYPE WORKBENCH

版本化交互原型工作台

把一段需求，整理成能点击的 HTML 原型、能交给开发的说明文档，以及以后查得到的版本记录。需求再变化，也不用把所有内容推倒重来。

看完整流程 打开当前示例
  • 页面可以真实点击
  • 文档和原型同版本
  • 可关联提交与 MR / PR

它解决什么问题

让需求不只停留在文字里

同一份需求会同时变成四类成果，让产品、设计、开发和测试看到的是同一件事。

01 · 可体验

可点击的 HTML 原型

不是静态截图。按钮、表单、成功和失败状态都可以真实演示，方便尽早发现理解偏差。

02 · 可执行

开发与测试文档

开发知道要实现什么，测试知道要验证什么。不需要重新从聊天记录中拼接完整需求。

03 · 可迭代

清楚的版本链

从 v1.0 开始，每次变化产生 v1.1、v1.2。既能只看本次变化，也能查看当前完整要求。

04 · 可追溯

提交和 MR / PR 关联

一个版本可以关联原始代码、实现提交和评审链接，之后能够准确查看这一版到底改了什么。

从想法到交付

一条能反复迭代的工作链

点击左侧步骤，查看每一步由谁参与、解决什么问题、留下什么成果。

第 1 步 · 输入

先说清楚要解决什么

可以是一份需求文档，也可以是一段清楚的描述。Skill 会先判断这是新页面、需求变更，还是已有原型需要调整。

这一阶段留下 需求来源和本次范围

与 DEV 的关系

原型负责讲清楚，DEV 负责做进真实系统

两边不是重复工作。原型先把交互和规则跑通，DEV 再使用项目已有框架、接口和组件完成正式实现。

Design 阶段

由这个 Skill 产出可评审的设计事实。

  • 可点击 HTML，提前体验关键路径
  • 当前完整开发规格和本版变化
  • 测试场景、失败结果和边界条件
  • 每条要求都能通过稳定编号找到
版本文档
稳定编号

DEV 阶段

开发读取确认后的完整规格并进入真实代码。

  • 使用项目自己的 React、Vue 或其他框架
  • 接入真实接口、权限和数据处理
  • 提交代码并关联当前版本与 MR / PR
  • 测试对照同版本文档验证一致性
重要边界：默认情况下，这个 Skill 只负责原型和规格，不会自动修改正式业务代码。只有明确进入 DEV 实现阶段后，才由开发流程处理真实项目。

常见场景

不同项目，可以从不同位置开始

选择一个最接近的情况，查看 Skill 会如何处理。

从 v1.0 建立第一份共同标准

适合新模块、新菜单或没有现成原型的项目。先确定一个可独立评审的页面，再形成第一版完整交付。

  1. 01创建页面范围和 v1.0 基线。
  2. 02生成 HTML 原型、开发文档和测试文档。
  3. 03评审确认后，把原型标记为与 v1.0 对齐。

放到其他项目怎么用

安装一次，然后在目标项目里直接提需求

原型和文档会生成在目标项目自己的工作区，不会复用本仓库里的登录示例。

第 1 步

安装 Skill

告诉 Codex 仓库、Skill 子目录和版本，它会安装纯 Skill 包，不会安装测试原型。

请使用 skill-installer 安装：
仓库：Sean-XL196/versioned-prototype-workbench
路径：skill/versioned-prototype-workbench
名称：versioned-prototype-workbench
第 2 步

在项目中提出需求

说明页面、目标和关键交互。资料不完整时，Skill 会先确认影响结果的问题。

使用 $versioned-prototype-workbench，
根据这份需求创建 v1.0 规格文档
和可交互 HTML 原型。
第 3 步

评审、迭代、交接

打开工作台查看原型和文档。需求变化时继续追加版本，确认后交给 DEV 按完整规格实现。

继续使用 $versioned-prototype-workbench，
把这次修改形成 v1.1，
先更新文档，再按确认内容调整原型。

不同角色看到什么

同一版本，给每个人合适的信息

业务和产品：直接体验要交付的效果

无需阅读代码。通过可点击原型确认流程、文案、状态和关键规则，并通过“本版变更”快速了解这次改了什么。

  • 可点击 HTML 原型
  • 本版变更说明
  • 历史版本和差异入口

能力边界

它擅长什么，也明确不替代什么

适合交给它

  • 把需求整理成可点击的页面原型
  • 为每次需求变化建立清楚版本
  • 同步产出开发和测试文档
  • 拆分过大的多菜单原型
  • 关联 Git 提交、MR / PR 和固定 Diff

需要后续流程处理

  • 正式系统的框架代码与后端接口
  • 真实账号、权限和生产数据
  • 上线发布、性能和安全保障
  • 业务负责人尚未确认的规则选择
  • 未经授权直接修改正式业务代码
